# 15 类歌曲情绪识别服务设计

## 目标与边界

构建一个部署在公司内网、可由评测机访问的 HTTP 服务。服务接收歌曲音频 URL、标题、艺人和歌词，返回 15 个二级情绪中的最高置信标签，并可选返回第二标签和真实判定证据。

服务必须实现 `POST /api/v1/emotion/recognize`，在 30 秒内返回，稳定支持至少 5 QPS、峰值 10 QPS，且不依赖运行时外部模型 API。线上按 CPU 可运行设计；GPU 只能作为可选加速，不是部署前提。

标签全集：狂欢、热血励志、活力、欢快、甜蜜、自信、浪漫、放松、治愈、思念、平静、孤独、悲伤、苦情、抑郁。

评测要求输出唯一 `top_emotion`。命题方确认同极性且合理的多种情绪可以同时成立，因此训练保留同曲多标签信息，推理时输出 15 类中分数最高者。

## 数据契约

官方训练数据来源为 `competition/data/emotion_songs_20260908_with_lrc.xlsx`。原始表不被改写。

- 6,016 条标注记录，5,097 首唯一歌曲。
- 15 类中，治愈 416 条，其他每类 400 条。
- 734 首歌曲有多个正向标签；同一歌曲的标签合并为一个多热标签向量。
- 滚词歌词缺失 586 条，文本歌词缺失 2,567 条，翻译歌词缺失 4,128 条。

PMEmo 仅用于音频下载、解码、特征提取和并发链路的回归测试；它不进入正式 15 类标签训练、阈值校准或准确率结论。

## 评测与数据切分

所有切分以 `歌曲id` 为不可拆分分组单位。绝不按 Excel 行随机切分。

1. 从唯一歌曲中分出约 15% 的锁定测试集，并按 15 类正向标签尽量分层。锁定集在模型选择前不读取评分结果。
2. 剩余约 85% 是开发集，在开发集内做 5 折歌曲级、标签分层交叉验证。
3. 每次实验同时输出：
   - 严格 Top-1：仅在单标签歌曲上计算；
   - 宽松 Top-1：预测命中该歌曲任一官方正向标签；
   - 15 类宏召回、逐类召回和混淆矩阵；
   - 含下载时间的 P50、P95、P99 延迟、错误率和单位成本。
4. 选择配置后仅在锁定集评估一次，固定模型结构、特征、融合权重和阈值。最终交付模型可用全部官方训练数据按已固定配置重训。

该流程用严格 Top-1 近似隐藏集的单一标签评分，用宽松 Top-1 反映训练标签中允许的情绪共存；两者均不等价于隐藏集成绩。

## 模型路线与选择原则

实现并比较以下四个版本，任何复杂版本只有在歌曲级交叉验证中稳定增益时才保留：

1. **歌词基线**：标题、艺人、文本歌词、滚词歌词和翻译歌词规范化后，用中英字符/词 n-gram 加线性概率分类器。
2. **音频基线**：下载并解码受限时长音频，提取节奏、响度、能量、频谱、动态范围和人声相关特征，用树模型或线性模型输出 15 类分数。
3. **双模态融合**：歌词与音频分别打分，使用开发集的折外预测训练标签级融合器。歌词缺失时，融合器只依赖可用模态。
4. **预训练编码器升级**：仅在许可证、模型资产大小和 CPU 压测均通过时，引入可离线部署的量化多语文本或音乐音频编码器，并与版本 3 做同规则比较。线上不得调用外部模型服务。

默认交付选择满足硬约束的版本中，严格 Top-1 最高者；若差距小于 0.5 个百分点，选择宏召回更高、P99 更低且成本更低者。宏召回低于 80%、单次成本超过 0.1 元、30 秒超时或 10 QPS 不稳定的版本不可交付。

## 在线请求链路

```text
HTTP 参数校验
  -> 带连接与总时限的音频下载
  -> 解码并截取受限音频
  -> 词文本规范化与语言可用性检查
  -> 音频特征 / 歌词分类器并行推理
  -> 标签级融合、排序与置信度校准
  -> 生成来自实际输入和特征的 evidence
  -> JSON 响应与延迟日志
```

### 输入处理

- `audio_url` 必须直接 GET，接受带过期签名参数的 URL；下载过程限制连接时间、总时间、文件大小与最大解码长度。
- 歌词优先使用纯文本歌词；缺失时从 LRC 去时间戳；外语歌曲可将翻译歌词作为补充字段而非替代原文。
- 标题、艺人和一级曲风标签只作为辅助文本或离线特征，不能伪造不存在的歌词或音频证据。

### 输出与证据

- `top_emotion` 必须是 15 类精确字符串；`top_confidence` 四位小数，范围为 0 到 1。
- `second_emotion` 必须不同于 Top-1，且其置信度不高于 Top-1。
- `evidence` 仅可包含本请求真实测得的音频数值、实际命中的歌词短句、实际可用模态和模型版本。无歌词或下载失败时明确说明缺失模态，不能编造特征。
- 参数问题返回 JSON 400；下载、解码和推理错误返回 JSON 4xx/5xx，绝不返回编造的情绪标签。

## 性能、成本与可靠性

- 请求总预算 25 秒，给评测机和网络保留余量；每个阶段有独立可观测耗时。
- 线上模型、向量化器和标签配置启动时加载；请求不加载模型权重。
- 以歌曲 ID 和规范化 URL 做有限期缓存，缓存只优化重复请求，不是正确性前提。
- 线程池分别限制下载和 CPU 推理并发，防止峰值请求耗尽资源。过载时返回可观测的 JSON 错误，不丢失或挂死请求。
- 日志包含请求 ID、歌曲 ID、模态可用性、标签、各阶段耗时、状态码和错误原因；不打印完整歌词或签名 URL。
- 启动脚本、重启脚本、健康检查和 10 QPS 压测脚本随服务交付。

## 测试与验收

- 单元测试：请求/响应 schema、标签全集、歌词清洗、特征范围、融合排序、证据真实性和错误 JSON。
- 集成测试：本地 HTTP 服务、模拟音频下载成功/超时/损坏文件、歌词缺失、LRC 翻译、多语言输入。
- 回归测试：PMEmo 本地音频和官方歌曲表字段可被加载，但不得将 PMEmo 结果当正式分类指标。
- 负载测试：冷启动、持续 5 QPS 和峰值 10 QPS，记录 P50/P95/P99、错误率、CPU/内存和模型磁盘占用。
- 自测报告必须列明数据版本、歌曲级切分种子、每个候选版本、锁定测试集结果、成本估算与已知限制。

## 交付物

1. 内网 HTTP 服务、启动/重启/健康检查脚本。
2. 数据预处理、训练、评估、推理完整代码和依赖清单。
3. 本地模型资产及其许可证、来源、体积与加载方式说明。
4. 成本估算表，包含单次 P50/P99、CPU 核秒、模型存储、10 QPS 所需实例规格和月成本推导。
5. 架构运维手册，含部署步骤、配置、日志监控和至少五项故障排查。

## 已知限制

隐藏集包含未发放的边界或混合情绪歌曲，离线结果不能承诺隐藏集成绩。设计通过歌曲级验证、严格单标签代理评测、混淆标签分析和真实证据审计降低过拟合风险，但最终效果仍以命题方盲测为准。
